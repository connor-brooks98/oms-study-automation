## Reason and public interface

Task 1.3 exposes `KnowledgeRepository.initialize()` but Sol-1 is forbidden
from editing central startup or migration files. Without a Sol-0 registration,
application construction never creates the three additive source-trust tables.
The proposed call is schema registration only; it does not add routes, enable a
flag, or activate a consumer.

The exact public app-state contract is:

| State name | Type | Semantics |
| --- | --- | --- |
| `app.state.knowledge_repository` | `KnowledgeRepository \| None` | The initialized repository when construction and `initialize()` succeed; `None` after any initialization failure. |
| `app.state.source_trust_available` | `bool` | `False` initially and on failure; after successful initialization, exactly `resolved.feature_flags.is_enabled(FeatureFlag.SOURCE_TRUST_V1)`. |

Every future source-trust consumer must require both
`app.state.knowledge_repository is not None` and
`app.state.source_trust_available is True`. The existing
`source_trust_v1` default remains off outside explicit development/test
configuration; this proposal does not register routes or turn that flag on.

Initialization runs even when the flag is off because it is additive,
idempotent schema registration. If construction or initialization raises, the
fixed warning below is the only diagnostic, the repository state is `None`,
availability remains false, and application startup continues. The diagnostic
does not include exception text, paths, source content, or secrets.
