## Transaction and trust behavior

Each write acquires SQLite `BEGIN IMMEDIATE` before reading collision state,
then relies on the shared uniqueness/FK constraints. This intentionally serializes
writers and avoids read-then-insert races; no retry service, provider, custom locks
or second persistence layer was introduced. The repository targets this project's
SQLite database; a future alternate backend requires replacing that transaction
locking statement. SQLite's existing five-second busy timeout remains in effect.

Complete import/attempt collisions are checked against immutable canonical content.
An identical export returns its stored receipt. Identical attempts from a distinct
export append provenance rows without inflating attempts. All original rows,
including duplicates and held bodies, are retained. Changed export/question/attempt
content yields a conflict receipt only after rollback, with zero inserted counts;
unexpected database/write failures propagate after the same rollback.

Public commit revalidates Python values before JSON serialization, recomputes the
preview and digest, and ignores supplied readiness/issues. This prevents modified
nested dictionaries or constructed previews from bypassing validation, including
nonfinite values that JSON serialization would otherwise mask as null.

Native writes use the same transaction path, a deterministic internal export ID,
required attempt identity, and internal `study_hub_attempt` provenance. Inputs are
trusted server-graded outcomes with owner-associated learner identity; this API
does not validate a browser's claimed correctness. Public playback is not wired
to it. Unknown results and absent timestamps remain unchanged in keyset reads.

## O-approved narrow amendments

1. A metadata-only shared question may receive its first non-null content/hash
   transactionally. Existing non-null hashes are immutable: a different body is
   a conflict, even when the old body was invalid/held. Original import rows and
   attempts remain unchanged. Raw held bodies stay in `row_json`; their hash is
   retained while `native_question_json` stays null and `body_ready` false.
2. External `accepted` topic labels do not establish reviewer authority. Exact
   submitted topic metadata stays in raw rows, but effective analytics emits
   pending proposals until an audited `set_topics` call supplies trusted review.
   Reviewed labels supersede corresponding raw proposals. Existing reviewed
   mappings cannot be overwritten by a later import. Topic audits record old/new
   JSON, content hash, review time and `{"actor": reviewer_context}`.
3. Content enumeration requires the learner's own ready body-bearing import row,
   not merely a QID/results row matching another learner's shared question.
   The owner boundary must use `list_ready_questions` or `review_rows`; global
   `get_question` is reserved for trusted internal operations.
