## Persistence and reporting

Uses the approved `study_sessions` and `study_session_questions` tables and Q's actual bank contracts. A server UUID is issued per session and per delivered question. Full `(quiz token, version, canonical native content SHA-256, stable question ID)` is serialized and hashed into a 71-character `QuestionKey.question_id`, preserving the shared 200-character limit.

Before returning grading feedback, C commits `{submission,result,feedback,topics}` to `selected_answer_json` with server submission time and optional duration. It releases that transaction, invokes Q's atomic `record_attempt`, validates the returned owner/key/identity/result/time/duration, and links `bank_attempt_id` in a new transaction. This uses the existing approved columns; it adds no outcome/aggregate table. A crash before or after the bank commit retries the same staged inputs, even after the publication changes, without regrading. A different selection/duration conflicts. Only acknowledged feedback is restored as graded UI state. Closing blocks new answers but still allows exact staged replay.

Progress scans one owner's actual `AttemptFact` records with Q's cursor. Global event deduplication precedes source/topic groups. Only accepted mapped labels group events. First selection occurs globally before topic grouping, so a repeat with a new label cannot become a first attempt for that topic. Repeats count extra events for the same immutable question key. A group with multiple events and any missing occurrence time, or a tied earliest time, has ambiguous ordering and is excluded from first-only accuracy. A single undated event can count as first; undated coverage remains explicit. Omitted/unknown imported results stay distinct, and only correct+incorrect enter accuracy. No pass/readiness model, aggregate store, browser-history migration, or pass-tracker replacement.
