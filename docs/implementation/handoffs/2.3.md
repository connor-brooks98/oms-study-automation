`StoreKey.course(course_id, exam_id)` renders exactly
`course:{course_id}:exam:{exam_id}`. `StoreKey.literature(course_id)` renders
exactly `literature:{course_id}`. Identifiers are bounded, slug-safe, and
cannot contain the namespace delimiter. Display names are derived only from
the validated local key, sanitized, and capped at 100 characters. Provider
store/document identities are persisted separately and are never derived from
or reused as local names.

The explicit state graph covers the required indexing phases, retryable and
terminal failure, stale generation recovery, and deletion. A failed remote
document delete deliberately leaves the durable document in `DELETING`; a
later retry can finish `DELETING -> DELETED` without falsely claiming success.
Every unlisted transition, including self-transitions, is rejected.

The repository uses the existing `Base` and `Database.session()` conventions.
`ProviderStoreModel`, `ProviderDocumentModel`, and `IndexJobModel` are additive
owned rows. Store generations use a unique `(store_key, generation)`, a unique
provider identity, and a partial unique current-key index, allowing a stale
orphan and a different current replacement to coexist. Document and job
identity/idempotency constraints are database-enforced. Metadata is validated
JSON and round-tripped canonically.

`GeminiFileSearchAdmin` uses one `async with GeminiClientFactory.client()` per
operation. `ensure_store` checks the current opaque provider identity, commits
the old generation `STALE` before replacement after a translated 404 (or a
missing result), and leaves that stale state committed when replacement
creation fails. Non-404 provider failures do not mutate local state. Listing
only maps remote documents into local records; upload/import/wait behavior is
not included. Delete calls the injected async document surface and only marks
`DELETED` after the remote call succeeds.

schema boundary for existing databases; no destructive alteration or data
backfill is required. `app.py` and `cli.py` already reach `Database.migrate()`
through `migrations.py`, so no application bootstrap hunk is proposed.

untouched. Sol-0 owns central migrations and must compose it with any other
schema-version proposal, rerun migration/bootstrap and existing DB tests, and
