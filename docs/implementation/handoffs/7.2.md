## Produced interfaces

- `AnkiLearningRepository.record_sync(snapshot) -> AnkiSyncRun` accepts the frozen Task 7.1 snapshot or its exact approved serialized mapping, validates all trust-boundary fields, appends an immutable receipt, and replaces the current note-state view only for changed content.
- `AnkiLearningRepository.latest_note_state(note_id) -> AnkiNoteLearningState | None` reads the current note state; deleted notes in a replacement snapshot are absent from the current view.
- `AnkiLearningRepository.latest_sync_health() -> AnkiSyncHealthView`, a subtype of the frozen Task 7.1 `AnkiSyncHealth`, adds `last_synced_at` and the nonblocking `staleness` label.
- `AnkiLearningSync.build_and_upload() -> AnkiSyncRun` uses only injected reader/uploader ports. It reads, validates/minimizes, uploads, and records in that order. Reader or uploader failure propagates and leaves the repository unchanged.
- `AnkiStalenessThresholds` defaults to 24 hours and 7 days and may be supplied per repository without central configuration changes. Labels are `fresh` for age `< 24h`, `stale` for `24h <= age <= 7d`, `very_stale` for age `> 7d`, and `never_synced` before the first receipt.

## Invariants and judgment calls

- Task 7.1 `learning_contracts.py` remains untouched. This task reuses its `AnkiLearningSnapshot`, `AnkiNoteLearningState`, and `AnkiSyncHealth` types rather than defining duplicate learning records.
- Snapshot content hashes use canonical JSON over health plus minimized note fields, sorted note/card/tag order, and omit only per-snapshot timestamps. A retry with the same content hash appends a `no_change` receipt and creates no duplicate note-state rows.
- Changed hashes replace the current note-state map while prior receipts and prior note-state rows remain auditable. A previously seen hash may become current again without duplicating its hash-addressed note rows.
- The serialized upload payload contains only `notes`, `health`, and `snapshot_at`; note payloads contain exactly the Task 7.1 minimized fields. Extra fields, including private collection data, card HTML, and media, fail closed before upload or persistence.
- Timestamps must be timezone-aware and are normalized to UTC. The injected clock is used for receipt time and current staleness checks. Future timestamps are treated as fresh; staleness never blocks Study Hub.
- The implementation is process-local and intentionally does not add implicit DDL, database bootstrap, application wiring, routes, config, flags, or live upload behavior.
