## Deliverable

- Produced prompt version: `objective-extraction-v1`.
- Produced interfaces: `ProposedObjective`, `SuggestedObjectiveLink`, `ObjectiveExtractor.extract(source_revision_ids)`, `ObjectiveService.approve(...)`, `ObjectiveService.merge(...)`, `ObjectiveService.retire(...)`, and unregistered `build_objective_router(...)`.
- Extraction boundary: only unretired, claim-supporting evidence from declared READY Gate 2A revisions reaches the injected proposal generator. Proposed evidence and scope are rechecked with the accepted Gate 2A policy before a proposal is returned.
- Deterministic consolidation: all exact normalized verb/concept/scope duplicates combine in a complete first pass before any ambiguous comparison. Lecture IDs are canonicalized as a sorted set so equivalent multi-lecture scopes have one proposal identity. Only evidence-overlapping ambiguous near-duplicates reach the optional consolidator, which receives proposed objective text and evidence IDs rather than source text or unrestricted sources.
- Resource bounds: the route and domain accept at most 32 source revisions per extraction. Evidence count, per-unit text, aggregate model input, proposal count, proposal fields, identifier collections, and suggested links are capped before repository/model work can grow without bound; identifier deduplication is set-backed and linear.
- Human authority: extracted proposals persist separately with `pending`, `approved`, `merged`, or `retired` review disposition. They do not create a `LearningObjective` until `ObjectiveService.approve`; approval atomically revalidates READY evidence and creates the approved objective under the same SQLite write claim.
- Review lifecycle: pending merges preserve the target proposal, append source revision/evidence/link suggestions, and durably mark the source as merged. Pending retirement creates no authoritative objective; approved retirement changes the objective and proposal under one SQLite write claim, preserving immutable evidence links and rolling both states back together on failure. DDL and record validation fail closed for inconsistent disposition links.
- Routes: all five manifest routes are implemented with private/no-store responses and application-owned auth/CSRF inheritance. The router is not registered on the production app.
- Review panel: the isolated browser client/panel supports extraction, approve, merge, retire, evidence preview, duplicate-action suppression, accessible initial-load retry and preview-failure recovery, semantic disclosures/forms, existing `sh-*` primitives, and escaped untrusted text.
