## Rulings and limitations

- The question schema root is an `anyOf` union of the three wire-bearing models;
  enums and nested option/claim definitions remain in `$defs`.
- `QuestionValidationResult.codes` is intentionally generic because Task 5.6 owns
  the validator-code vocabulary. A later task can add structured diagnostics with
  a schema version bump if string codes prove insufficient.
- Claims are allowed to be an empty collection because the approved design says
  every present claim must carry evidence, but does not require a claim count;
  semantic claim coverage belongs to Task 5.6. This is reversible at the model
  boundary and costs a schema change if later required.
- `QuestionVersion` provenance is required because it is a derivative record;
  draft creation remains independent through the nested `BoardQuestionDraft`.
  Evidence IDs remain optional pending the bounded evidence-packet contract.
- The shared exporter and its snapshot test are not modified; the mismatch above
  must be resolved by the Sol-0 integration lane.
